## 工作方式（快、准）

1. **读到哪改到哪**：打开本节点旧产出 + 变更点 + 上一节点变更摘要。
   - 本节点不受影响 → 正文不动，写 `reopen_impact.impact: none`，无需澄清则直接过。
   - 有影响 → **只改相关几段**，结果**直接覆盖本节点原文件**（路径即 `{{final_output_path}}` / 各角色既有 `02-plan-*.md`、`03-tasks-*.md` 等），禁止另存 `*-vN` 副本，禁止整篇无故重写。
2. **禁止一味追加（硬约束）**：与 change / 上一节点结论冲突时，必须在**原文位置**改掉旧说法，使全文口径一致。
   - **正文 / 方案 / 任务 / 验收 / 结论节**：改原段落、原条目、原表格行；不要在文末再堆一段「本轮补充：…」却留下旧 Redis/旧流程原文。
   - **澄清清单**：优先**修订**已有 Q 的 `as_is` / `question` / `suggestion` / `answer`（或删掉已作废项）；`as_is` 须零熟悉度可读（哪块功能 + 哪个接口/入口 + 当前行为）；`suggestion` 须用大白话写清「选什么 + 做完后会怎样」；**禁止**为 change 已写死的事再开 Q8/Q9…「覆盖上一轮」；change 已明确的内容**直接改需求正文，不要再澄清一遍**。
   - **元数据 / 范围 / 风险等 YAML**：就地更新字段值，不要另起一套并行描述。
   - 仅当出现**旧文档与 change 都未覆盖**的新歧义时，才允许新增澄清项或新小节。
3. **倾向（非绝对）**：
   - 变更点落在业务/验收，或上一节点改了需求 → 本节点（及之后）更可能要动
   - 变更点落在方案/接口/表，或上一节点只改了计划 → 需求可 `none`，计划及之后更可能要动
   - 仅实现细节 → 前面文档常 `none`，从任务或编码起再改
4. **需求节点**：变更点触及业务时，**就地改** `{{requirements_doc}}`（`01-requirements.md`）里冲突的正文与清单，**不要**因「文件已存在」就跳过正文、只往 checklist 追加；change 清单只在 `changes/change-vN.md`，不要拿 change 文件当需求正文去覆盖整文件另存。
5. **意图**：有缓存则沿用角色/仓/分支；本注入不替代意图节点。
6. **定稿须带** ``reopen_impact``（写在被覆盖的原文件 YAML 区；已复核清单也放在这里，不要另开 metadata 字段）：

```yaml reopen_impact
impact: none
summary: "没改 / 或一句话说明改了什么（下一节点靠这段快速定位）"
touched_anchors:
  - "US-1"
reviewed_changes:
  - changes/change-{{change_version}}.md
```

- `impact`：`none` 或 `patch`
- `touched_anchors`：实际改过的位置（编号或章节名）；没改写 `[]`
- `reviewed_changes`：已对照过的 **change** 文件列表；在原有列表上**追加**本轮 `changes/change-{{change_version}}.md`，不要删已有项；**不要**写 `00-requirement.md`
- `patch` 时引擎会把**本节点之后**的确认打回 pending；`none` 不动下游
- 引擎也会自动补写本轮 change；续跑读各节点 md 的 `reopen_impact.reviewed_changes`，不靠 change 文件的 `last_node`

## 以下是本节点常规阶段提示词

从这里往下是**本节点日常交付用的同一套阶段提示词**（产出结构、YAML 块、澄清/定稿、`--auto` 与人工确认等），与首轮从 0 到 1 时该节点看到的模板一致，**不是**另一份「原始需求正文」。

阅读与执行顺序：

1. **先遵守上文 reopen 注入**（变更点、**原地改冲突**、禁止一味追加、`reopen_impact` / `reviewed_changes`）。
2. 再按**下方阶段提示词**完成本节点该做的事（格式、门禁、角色范围等仍有效）。
