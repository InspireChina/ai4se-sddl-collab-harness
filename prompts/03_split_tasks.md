## 写作与提问语言（**全程必须遵守**）

- **用人话写，别像 AI**：任务文档要像资深工程师写给同事看的内部技术文档，直白、具体、不绕。**禁止** AI 腔：堆砌「综上所述」「值得一提的是」「首先…其次…最后」、过度对仗排比、空洞套话、emoji 装饰、无意义的礼貌用语。该用要点用要点，该一段说清就一段。
- **澄清问题前先写清现状（AS-IS）**（**质量硬门槛**）：每个决策项若涉及现状，必须先写 `as_is` 再提问。对项目零背景的人**只读这一条 `as_is`**，就能定位「哪块功能 + 哪个接口/入口 + 现在怎么跑」；禁止「已有类似实现」「现网支持」等空话。
  - **必含**：①业务功能名；②入口（HTTP method+path / Job / MQ / 前端页面或按钮）；③当前行为（谁调用、关键结果与限制）；④无现成入口写「无现成接口/入口，属新增」。
  - **坏例**：「取消相关接口已存在。」**好例**：「订单取消：计划要点名的 `POST /api/orders/{id}/cancel` 已在代码中；入参含 `cancel_reason`；已支付走退款；管理端无对称接口。」
  - 全新增则 `as_is` 留空。向用户提问时**先展示完整 `as_is`，再问问题与推荐（含效果）**。
- **推荐（`suggestion`）必须写清落地效果（大白话）**：选了什么 + **做完后**任务怎么拆、哪个入口怎么落、调用方/用户看到什么、相对现状多了/少了/不变什么。禁止只写「建议拆成两条 / 建议复用」。**坏例**：「建议复用现有取消接口拆任务。」**好例**：「建议一条任务改 `POST /api/orders/{id}/cancel` 放开管理端调用，前端另开一条加管理端取消按钮。做完后：C 端取消不变；管理端详情也能取消并填原因；两边共用同一接口与退款逻辑。」

## 定稿正文模板（**必须遵守**）

### 一条 Task = 一种落地物

每条 Task 只选**一种类型**，不要把「改表 + 写接口 + 写前端」捆成一条：

| 类型 | 边界 |
|------|------|
| **API** | 一个 HTTP/RPC 接口（或同资源、同次交付的强绑定方法组，如同一 Path 的 GET+PUT） |
| **领域模型与表结构** | 同一聚合的模型/枚举/表字段/迁移/索引 |
| **定时任务** | 一个 Cron/调度 Job 的新增或改造 |
| **消息消费/生产** | 一个生产者或一个消费者 |
| **公共组件/方法** | 一个可复用方法或一个小组件 |
| **前端页面/交互** | 一个页面或一块独立交互 |
| **配置与基建** | 一类配置/开关/权限点/路由注册/开通脚本（不掺业务逻辑） |
| **联调与对接** | 一段对外部系统或双端对齐的对接 |

编号统一 `TASK1`、`TASK2`…；标题用业务话（如「取消订单接口」），禁止空泛「实现某某模块」。

### 文档结构

「角色与版块」+ 顶部 YAML 之后，正文按此顺序：

1. **任务总览**（表）
2. **依赖与执行顺序**（一行箭头即可，如 `TASK1 → TASK2 → TASK3`）
3. **任务详情**（每个 `### TASKn：标题` 一节）

总览表列：

| ID | 类型 | 标题 | 归属 | 依赖 | 一句话目标 |
|----|------|------|------|------|------------|

归属填「后端」或「前端」（与本次角色版块一致）。

### 每条 Task 共通字段（必写）

- **类型** / **归属**
- **要做什么**：一句话说清交付物
- **改哪里**：层/模块（不强制列全文件路径）
- **不做**：明确边界，防加戏
- **完成标准**：可验证的几条
- **依赖**：无，或 `TASKm, …`

### 按类型加写（有则必详）

| 类型 | 额外必写 |
|------|----------|
| **API** | **接口契约**：Method/Path、鉴权、请求/响应示例（JSON）、错误码、幂等约定；**逻辑细节**：逐步处理流程 |
| **领域模型与表结构** | 字段/枚举/索引/迁移策略、不变式、领域入口方法；**逻辑细节**（校验与流转） |
| **定时任务** | 调度表达式、触发条件、批量与失败重试、是否可重入；**逻辑细节** |
| **消息消费/生产** | Topic/Tag、消息体、消费幂等、失败策略；**逻辑细节** |
| **公共组件/方法** | 方法签名、入参/出参、适用场景、调用方约束 |
| **前端页面/交互** | 入口路由、关键交互步骤、调用的 API、空态/错态 |
| **配置与基建** | 配置项清单、默认值、生效方式、开通依赖 |
| **联调与对接** | 对端系统、请求/响应、超时重试、降级 |

- API/消息的 JSON 与错误码写在该 Task 内，不要文末汇总

## 拆分策略

- 单元/API 测试不在 `implement_code`；由 `verify_tests` 编写执行
- `requirement_type = new`：表结构/基建 → 领域与 API → 联调/前端；每条 Task 按类型写全细节
- `requirement_type = existing_change`：含现状确认/兼容/回归；标注存量影响

## 写作约束

1. Plan 只给接口清单与方向；Task 按类型写全契约与逻辑细节
2. 决策未完成不得定稿；未 `approved` 不得进入实现
